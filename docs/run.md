# ラン（run）

2026-11-07 作成。前提は `docs/product.md` 3〜4（コアループ、ラン）、9（試遊ページ）と `docs/protocol.md`。読む人は Host（ラン画面・試遊ページ）と API の実装者。
節番号は `run#A.5` のように参照する。A 部が規約、B 部が理由。数値のうち「暫定」と書いたものは定数として持ち、実機で変える。

# A. 規約

## A.1 用語

| 用語 | 意味 |
| --- | --- |
| ラン | スタートから成績表までの 1 回。`run_id` を持つ |
| 山札 | ランの開始時に確定する、出すゲーム（`post_id`）の並び |
| 計画 | ランの作成時に凍結する値の組。山札、位置ごとの `is_new` と `miss_below`、ランの seed（A.3） |
| 記録 | サーバが持つ、手番の結果の列。手番 0 から順に 1 つずつ足され、抜けがない（A.3） |
| 周回 | 山札を 1 回通ること。エンドレスは周回ごとに速くなる |
| 手番 | ランの中の 1 本。0 始まりの番号 `t` を持つ。山札の位置と周回は、計画とそれより前の手番から決まる（A.3）。1 手番 = 1 セッション（`protocol.md`） |
| スロット | 画面上の iframe の置き場。N（表示中）、N+1、N+2 の 3 つ |
| 幕間 | 手番と手番の間に Host が描く画面。次のゲームの動詞と入力アイコン |
| 結果フラッシュ | 手番の終わりに Host が描く 0.5 秒。点と偏差値、またはミス |
| 新作枠 | 山札に 1 本含まれる、校正中のゲーム（`product.md` 7）。成績に入らず残機も減らない。校正済みが足りない間は複数になる（A.2） |
| skip | 遊んだ結果にならなかった手番（満了、`error`、読み込みの skip）。成績の分母から外れ、残機も減らず、そのゲームは以後の周回に出ない（A.6） |
| 読み込みの skip | skip のうち、出す時点で先読みが済んでいなかったもの。3 本目でランは通信エラーで終わる（A.6） |

## A.2 ランの種類と定数

| | エンドレス | デイリー |
| --- | --- | --- |
| 山札の本数 | 12（暫定）。出せるゲームが足りなければ短くなる（下） | 10。出せなくなったお題のぶん短くなる（下） |
| 周回 | 上限まで繰り返す | 1 周 |
| 上限（手番） | 50 | 10 |
| 速度 | 周回 k（0 始まり）で `min(1.5, 1 + 0.125 × k)`（暫定）。1/8 刻み | 1.0 固定 |
| 残機 | 3。偏差値 40 未満でミス（閾値は暫定） | なし |
| 新作枠 | 山札に 1 本（足りないときは下） | 山札に 1 本 |
| 記録 | 到達手番数。総合偏差値を併記 | 平均偏差値 |
| 記録になるラン | 毎回 | 同じお題・日付では初回のみ（`data-model.md` I16）。2 回目以降は練習（成績表は出るが保存しない）。日のうちにお題が出せなくなって山札が変わっても、2 回目以降は練習 |
| 山札の決め方 | 校正済みの公開ゲームから、直近 7 日（暫定）にその人が引いたものを除いて抽選 | お題と日付から決定論的に（お題の 10 本のうち、作成時点で出せるもの） |
| 共有 | `/r/<run_id>`。同じ山札（今もランに出せる投稿だけ）で新しいランを作る | `/t/<theme>/<date>`。同じお題・日付。リンクが指すのはその日のお題で、山札そのものではない（出せなくなったお題のぶん、共有した人より短いことがある） |

エンドレスの山札が規定どおりに組めないとき（サービス開始直後、校正済みが少ない間だけ起きる）は、あるだけで組む。

- 正規枠（11 本）に校正済みが足りなければ、足りない分を未校正で埋める。埋めた手番は新作枠と同じ扱い（`is_new: true`、`miss_below: null`。残機は減らず、等速の記録は校正に入る）
- 未校正が 0 本なら新作枠なしで、校正済みだけで 12 本にする
- それでも 12 本に満たなければ山札を短くする（最小 1 本。周回は同じ規則で回る）。出せるゲームが 0 本なら `POST /runs` は 409 `no_games`
- 直近 7 日の除外で 12 本組めなくなるときは、引いた日が古いものから除外を外す
- 同じゲームを山札に重ねない

**どの山札も、ランの作成時点でランに出せる投稿だけを含む**（#175）。「ランに出せる」は `scoring.md` A.8 の正規枠か新作枠に当たること（`post_eligibility`）で、新規・`from_run`・デイリーのどれも同じ基準を使う。`restricted` / `unpublished` / `removed` の投稿も、公開のまま校正状態が `review` / `invalid` になった投稿も入らない。サーバは作成時にこれを知っているので、計画に入れない。Host が「読み込めない」ことから推測するのは、ラン中に出せなくなった投稿と回線の問題だけになる（A.6）。

- エンドレス（新規）: 出せるゲームだけから抽選する（上）
- `from_run`: 元のランの山札から、今はランに出せない投稿を落として写す（A.3）
- デイリー: お題の 10 本（`theme_posts`）のうち出せる投稿を、お題の順のまま並べる。出せなくなったお題があると 10 本より短くなり、その日のうちでも作成の時点によって本数が違いうる。0 本なら 409 `no_games`

山札の本数より上限が小さい場合（デイリーの 10 本）は 1 周で終わる。エンドレスは 12 本なら 5 周目（速度 1.5）の途中で 50 に達する。

## A.3 計画と記録

ランの計画はサーバが作成時に凍結する。進行（次にどの手番を出すか、ミスか、いつ終わるか）は Host が計画から決める。記録はサーバが持ち、Host が送った結果を手番の順に足す。サーバは Host の進行を推測しない。

| 操作 | 内容 |
| --- | --- |
| `POST /runs` | `{mode, theme?, from_run?}`。計画を凍結して `{run_id, seed, deck: [{post_id, is_new, miss_below, time_limit}]}` を返す。`from_run` は共有リンクからの再現で、山札と `is_new` を元のランから写し、作成時点でランに出せない投稿（A.2）を落とす（残りの順は保つ。全部落ちたら 409 `no_games`）。`miss_below` は作り直す |
| `PUT /runs/{id}/turns/{t}` | 手番 `t` の結果。本文は結果の種類ごとに `{via: "guest", score, frames, inputs}` / `{via: "timeout"}` / `{via: "error"}` / `{via: "noload"}`（`scoring.md` A.2）。応答は下 |
| `POST /runs/{id}/finish` | ランを閉じて、凍結した成績表を返す。何度呼んでも同じ |

手番 `t` の値は計画から決まる。`packages/domain` の 1 つの関数を Host とサーバが使い、Host の申告は使わない。

| 値 | 求め方 |
| --- | --- |
| 山札の位置と周回 | 手番 0 は位置 0、周回 0。以後、手番ごとに山札の次の位置へ進み、末尾を越えて先頭に戻るたびに周回が 1 増える。それより前の手番で skip（満了・`error`・読み込みの skip）になった位置は飛ばす（A.6）。Host は自分が遊んだ手番から、サーバは記録から求める。記録は Host が遊んだ列の先頭部分なので（F10）、同じ値になる |
| `speed` | 周回から（A.8） |
| `is_new`、`miss_below`、`time_limit` | 計画の、その位置の値。ラン中に分布や校正状態が動いても変わらない。Host は `init.time_limit` に計画の値を入れ、Guest の `ready.duration` は使わない |
| `seed` | ランの seed `S` と `t` から。`x = (S + t × 0x9E3779B9) mod 2³²` を mulberry32 の 1 回ぶんの混合に通した 32 bit 符号なし整数（暫定。`GF.rng` と同じ混合） |

`PUT /runs/{id}/turns/{t}` の応答。`settled` は記録の長さ（次に足す手番の番号）。

| 状況 | 応答 |
| --- | --- |
| `t = settled` で、ランが開いていて、結果が `scoring.md` A.2 の条件を満たす | 記録に足す。200 `{settled, deviation, miss, calibration, ratio}`（`settled` は足した後の値。skip は `deviation` も `ratio` も `null`、`miss` は `false`） |
| `t < settled`（すでに記録にある） | 何も変えない。200 で、保存した値から同じ内容を返す。本文は見ない |
| `t > settled`（前の手番がまだ届いていない） | 何も変えない。409 `{error: "out_of_order", settled}` |
| `t ≥ settled` で、ランが閉じている | 何も変えない。409 `{error: "run_closed", settled}` |
| 結果が条件を満たさない | 何も変えない。422 `{error: "invalid_result", reason}`。記録は進まない。Host が送る結果では起きない（`scoring.md` A.2） |

ランが閉じるのは次のどれかで、閉じた後は記録に足さない。

- 記録に 3 回目のミスが入った（エンドレス）
- 記録に 3 本目の読み込みの skip が入った（通信エラー。A.6）
- 次の手番が無い（記録の長さが上限に達した、または山札の出せる位置が無くなった）
- `finish` が届いた
- ランの作成から 60 分（暫定）が経った。`finish` が来なくてもランは閉じる（サーバは読むとき・書くときに期限を見る。閉じるためのジョブは持たない）

- `miss` は計画の `miss_below` で判定した値で、Host の判定と必ず一致する。応答は表示用で、進行には使わない
- 山札の投稿がラン中に出せなくなっても計画は変えない。配信が止まる（`security.md`）ので Host の先読みが済まず、その手番は読み込みの skip になり、以後の周回には出ない（A.6、`moderation.md` A.3）

## A.4 スロット

| スロット | iframe | セッション状態（`protocol.md` A.5） | ロードするもの |
| --- | --- | --- | --- |
| N | 可視 | RUNNING / PAUSED / ENDED | すべて |
| N+1, N+2 | 不可視 | LOADING → READY → INITED（`start` は送らない） | コードと `required` アセット（上限 512 KB）だけ |
| それ以外 | 存在しない | DESTROYED | — |

- N+1 / N+2 はスロットの位置であって手番番号ではない。skip で手番番号が飛んでも（手番 5 を skip して 6 を出す）、スロットは「表示中」「次に出す」「その次」の 3 つのまま
- 不可視スロットに `start` を送ることはない。`init` は送る（`onInit` まで済ませて待つ）
- 生きている iframe は常に 3 枚以下
- N−1（直前の手番）は持たない。ランは戻れない

## A.5 手番の切り替え

手番 N の終わり（`end` 受理、監視タイマー満了、`error`）から次の手番の `start` まで。順序を変えない。

1. `end` を受けた瞬間に、Host が `score < miss_below` でミスを判定し、残機を減らす（A.7）。通信を待たない。3 機目のミスならこの時点でランの終わりが確定する
2. 結果フラッシュを 0.5 秒（暫定）描く。点と、ミスならその印。同時に手番の結果を送る（A.7 の送り方。応答の偏差値は届いたら表示に足す。進行には使わない）
3. ランが終わっていれば（3 回目のミス、または上限の手番が終わった）、幕間の代わりに「終了」を出して A.7 の手順で `finish` を呼ぶ。以下の手順は行わない
4. 幕間を 1.0 秒（暫定）描く。内容は N+1 の動詞と入力アイコン（`ready` の `verb` / `input`）
5. 幕間の終わりに N+1 が INITED なら `start` を送る。これが唯一の `start` 送信点
6. N+1 がまだ INITED でなければ、待たずにその手番を読み込みの skip にして `destroy` し（A.6）、N+2 を繰り上げ、空いたスロットを 7 と同じく計画の次の手番で埋めて 4 から繰り返す。3 本目の読み込みの skip なら、幕間に戻らず通信エラーでランを終える
7. `start` を送ったら、旧 N に `destroy` を送って iframe を外し、計画の次の手番を新しい N+2 として iframe を作り、`init` まで進める。上限の手番より先は作らない

結果フラッシュと幕間は Host の描画で、iframe の上に重ねる。この層が Host のものであることを、画面上端の固定ヘッダーと同じ見た目で揃える（ゲームが描く偽 UI と区別するため）。見た目と動き（ドリルの紙、赤ペンの印、ページのめくり）は `host-design.md` が決める。めくりは 4 の幕間の内側で行い、ここに書いた順序と長さを変えない。

## A.6 skip

遊んだ結果にならなかった手番は skip。判定するのは Host。結果の種類（`scoring.md` A.1）でいうと次の 3 つ。

| 結果 | 原因 |
| --- | --- |
| 読み込みの skip（`via: noload`） | 幕間の終わりに INITED でない（A.5 の 6）。最初の手番は、スタート画面で 10 秒（暫定）待っても INITED でない（下）。どちらも通信エラーの 3 本に数える |
| 満了（`via: timeout`） | 監視タイマー満了（`protocol.md` A.7） |
| `error`（`via: error`） | ゲームのコールバックで例外 |

skip の 3 つに共通の規則。

- 成績の分母に入れず、残機も減らさず、成績表には「—」で出す
- **手番は消費する**（上限 50 の 1 つとして数える）
- **以後の周回に出さない**: skip になった山札の位置は、そのランでは飛ばす（A.3）。先読み済みの手番が飛ばす位置に当たったら、捨てて作り直す
- 結果は `PUT /runs/{id}/turns/{t}` でサーバに伝える。記録は手番の順にしか足せないので、伝えないと後ろの手番も記録に入らない。送り方は遊んだ結果と同じ（A.7）

読み込みの skip だけの規則。回線の側の問題なので、ゲームの側の問題（満了・`error`）と分ける。

- **待たない**: 幕間の終わりに先読みが済んでいなければ、その場で skip にする。先読みは 2 手番ぶん先に始まるので、間に合わないのは回線が悪いか、ゲームが配信されていないとき。ランの最初の手番には幕間が無いので、スタート画面で INITED を 10 秒（暫定）待つ。スタートの操作は最初の手番が INITED になってから受け付ける。10 秒で INITED にならなければ、その手番を読み込みの skip にして、次の手番を最初の手番として同じように待つ（3 本目で通信エラー。スタート画面で待つのは最長 30 秒）
- **3 本目でランは通信エラー**: 1 つのランで読み込みの skip が 3 本（暫定）になったら、Host はランを終え、「通信エラー」と「もう一回」を出す。成績表は出さず、記録（エンドレスの到達本数、デイリーの初回）にもしない。サーバも記録に 3 本目が入った時点でランを閉じ、`ended` は `error`。それまでに受理した結果は、ゲームごとの集計にはそのまま残る
- ゲームごとの集計（`scoring.md` A.4）には入らない。満了と `error` は失敗として数える

山札の出せる位置が無くなったら、次の手番が無いのでランは終わる（上限に達したのと同じ扱い。A.3）。

サーバは結果を「無効」と返して skip にすることをしない。条件に外れた結果は記録に足されない（A.3）。Host は Guest の報告を同じ条件で確かめてから受け取るので、Host が送る結果は条件に外れない（`scoring.md` A.2）。

## A.7 残機とミス（エンドレス）

- ミスは `score < miss_below`。`miss_below` はランの作成時にサーバが「偏差値 40（暫定）に相当する生の点数」として計画に入れ（A.3）、Host はこれで `end` の瞬間に判定する。`miss_below` が `null`（新作枠、校正中）の手番はミスにならない。`via: timeout / error` の手番は skip でミスにならない
- サーバも結果を記録に足すときに同じ凍結値で判定する。Host とサーバの判定は必ず一致する
- 3 回目のミスでランは終わる。上限の手番が終わったときも同じ。Host はその場で「終了」を出す
- 結果の送り方: Host は終わった手番の結果を手番の順に持ち、記録にまだ無い最も古い手番から送る。応答が来ない、または `out_of_order` が返ったら、応答の `settled`（分からなければ手元で最後に確かめた値）の手番から送り直す。間隔は 1 秒から倍にして最大 8 秒（暫定）。ランが続いている間は送り直しをやめない
- `finish` を呼ぶ時点: ランが終わったら、遊んだ手番がすべて記録に入る（`settled` が遊んだ手番数になる）のを待って `finish` を呼ぶ。10 秒（暫定）待っても入らなければそのまま呼ぶ。入らなかった手番は記録に無く、成績表に「通信できなかった N 本は記録されていません」と出す。中断（A.9）からの `finish` も同じ。先読みの iframe は捨てる
- 記録はサーバが決める。手番の順にしか足さず、3 回目のミスが入ったら閉じるので、ミスを無視して遊び続けるクライアントがいても、結果を送らないクライアントがいても、記録は伸びない（F9）
- 記録は、遊ぶ側が見たランの先頭部分と常に一致する（F10）。通信が届かないと短くなることはあるが、手番の扱い（成立・ミス・skip）が変わることはない
- デイリーに残機はない。山札を最後まで通す

## A.8 速度

- 手番の速度は周回から決まる（A.3）。エンドレスは周回 k で `min(1.5, 1 + 0.125 × k)`、デイリーは 1.0
- 速度は 1/8 刻みの離散値（1.0, 1.125, 1.25, 1.375, 1.5）。`protocol.md` の `init.speed` はこの 5 値のどれか
- 同じゲームが周回ごとに速くなって戻ってくる。Host は幕間に周回数（「2 周目」）を小さく出す

## A.9 中断と再開

- `visibilitychange` で非表示になったら N に `pause`、表示に戻ったら幕間を出し直してから `resume`。幕間は 1.0 秒で、「続きから」と動詞を出す
- 非表示のまま 10 分（暫定）経ったらランを中断扱いにする。表示中の手番は結果を送らずに捨てる。記録に入った手番はそのまま残り、成績表は「中断」として出せる
- ページを閉じた・リロードした場合も中断。ランは再開できない（同じ山札で遊び直すなら `from_run` で新しいラン）

## A.10 新作枠

- 山札には、未校正のゲームがあれば校正中のゲームが 1 本入る（`product.md` 7）。位置はサーバが山札の中でランダムに決める。未校正が 0 本なら新作枠はない（A.2）。校正済みが足りず未校正で埋めた手番（A.2）も、以下は新作枠と同じに扱う
- 幕間では区別しない（遊ぶ側に「新作」と知らせない）。結果フラッシュでは偏差値の代わりに `gf:target` との比（`min(1, score / target)`）を出し、「校正中」と添える
- エンドレスで周回が進むと新作枠のゲームも速くなる。2 周目以降（速度 > 1.0）の記録は校正に入れない（`product.md` 5.2）

## A.11 成績表

ランの終わりに `finish` が返す凍結値を Host が描く。Host は計算しない。見え方は `host-design.md` A.8。

| 項目 | エンドレス | デイリー |
| --- | --- | --- |
| 見出し | 到達手番数「23 本」 | 平均偏差値 |

デイリーの記号列は偏差値を 5 段階に落とした文字列で、山札の位置ごとに 1 文字（山札が 10 本なら 10 文字）。作成時に出せないお題は山札に無いので、文字も無い。ラン中に出せなくなって skip になった位置（`moderation.md` A.3）は「—」。記号列の位置を人と揃えることはしない（#175）。途中でやめたラン（A.9）は記録にある位置までを出す（6 本目で中断なら 6 文字。残りを「—」で埋めると skip と見分けがつかないため）。段階の境界は暫定（60 以上 / 50 以上 / 40 以上 / 40 未満 / skip）。

## A.12 試遊ページ（下書き）

下書きのゲームを 1 本だけ遊ぶ Host。ランではないので残機も成績表もない。

- `mode: play` で `init` し、タップで `start`。終わったら結果と「もう一回」。「もう一回」は同じ iframe に `init` し直す（`protocol.md` A.6 の再利用）
- 速度スライダー（1.0〜1.5、1/8 刻み）。動かすと `init.speed` を変えて `init` し直す
- デバッグ表示: フレーム番号、残り時間、`GF.score`、速度、直近の入力（kind と data）、`error` の `message`、`gf:target` との比
- 「診断をコピー」: 直近のセッションについて、`end` が届いたか（届かず監視タイマーで終わったか）、`error` の内容、`GF.score` が 0 のまま終わったか、`frames < time_limit` で終わったか（遅い端末）、速度 1.5 で終われたか、を日本語の箇条書きにしてクリップボードに入れる。AI に貼る前提の文面にする
- 作者のセッションには印を付けて送り、校正に数えない（`product.md` 9）
- 公開ボタンはこのページにある。公開後のゲームページにはデバッグ表示も速度スライダーもない

## A.13 資源制御

- RUNNING は常に 1 枚。CPU を使うのはそれだけ
- 先読みはコードと `required` アセットまで。残りは N になってから。BGM はゲームにない（`game-contract.md` A.6）
- 固まった Guest は `protocol.md` A.7 の監視タイマーで終える。タイマーは Host の `setTimeout` で持ち、Guest が別プロセスで動くブラウザ（Chrome の site isolation）では Guest が無限ループでも発火する。`PerformanceObserver` の long task は補助で、500 ms 以上止まったフレームを数えて「重い」判定（skip と「このゲームは重すぎます」）に使うが、無限ループはタスクが終わらないので long task には現れない。主は監視タイマー
- Guest が Host と同じプロセスで動くブラウザ（iOS Safari）では、Guest の無限ループが Host の main thread も止めるので、監視タイマーも効かない。これはブラウザ側で止める（応答なしの警告）しかない。公開直後にサーバのジョブが決定論ハーネスで 1 回実行し（`mcp.md` A.9）、入力なしで固まるゲームを新作枠に出さない（`calibration = invalid`）ことで頻度を下げる
- 音は「タップしてスタート」で有効化する。初回訪問はミュートで始める（暫定）。Host の音量が `GF.audio.gain` の上限
- iframe の生成は手番の確定（A.5 の 6）で行う。スクロールや予測では作らない

# B. 解説（規則の理由と却下した案）

## B.1 計画をサーバが凍結し、進行は Host、記録はサーバが持つ理由（#151）

サーバに置く必要があるのは 3 つ。速度は検証の入力なので Host の申告を信じられない。ミスの閾値は分布からしか出せない。山札は共有リンクで同じ順を再現するのに要る。どれもランの作成時に決められる（速度は手番番号の関数、閾値は B.2 のとおり凍結してよい値）ので、計画として 1 回で渡す。Host は計画から進行を決め、サーバは結果を受けたとき同じ関数で同じ値を求め直す。

記録を手番の順にしか足さないのは、サーバに進行を推測させないため。足せるのは「記録の次の手番」だけなので、記録はどの瞬間も Host が遊んだ列の先頭部分で、通信の遅れ・消失・重複・順序の入れ替わりで中身が変わらない（F10）。届かなかった分は短くなるだけで、Host は古い手番から送り直せばよい。

却下した案: 手番を 1 つずつサーバが発行する（`POST /runs/{id}/next`。2026-11-07 から #151 までの設計）。発行時に `seed`・`speed`・`miss_below` を凍結してセッションを `open` で作り、`finish` で手番順に `sessions` を見て、後ろに結果のある未提出の手番は閾値があればミスに数えた。進行は B.2 で Host が決めるようになっていたので、サーバは行の集まりから進行を推測し直すことになり、推測が外れる状況ごとに規則が要った（#141〜#149 の未記載 45 点の約 3 分の 1）。`verification/RunSync.tla` で次の反例が出た。

- 前の手番の結果より後の手番の結果が先に届くと、`next` が未着の手番をミスに数えて `{done: true}` を返し、残機が残っているのにランが終わる
- 読み込みの skip の報告が届かないと、成績表ではその手番がミスになる
- サーバが結果を拒否すると、Host は残機切れ、成績表は中断になる
- `finish` を呼ばないランは閉じない

却下した案: 発行は残し、記録を「最初の未提出の手番で打ち切る」に変える。上の 1 つ目と 2 つ目は直るが、`next`、山札の通算位置、発行したまま捨てる手番、3 つ目と 4 つ目が残る。

却下した案: Host が山札を全部受け取り、サーバは `finish` で結果をまとめて受ける。ページを閉じると何も残らず、校正に使う結果も届かない。

## B.2 ミスの閾値を凍結して Host に渡す理由

偏差値は遊んだ人の分布から出す（`product.md` 5.2）ので、分布はサーバにしかない。かといって結果の応答を待ってから次の手番を始めると、回線が悪いときに幕間で待たされ、テンポが崩れる。逆に応答を待たずに進むと、3 機目のミスの応答が遅れたとき、終わっているはずのランで次の手番が始まる（F8 の違反）。

判定に必要なのは分布そのものではなく「この手番で何点未満ならミスか」という 1 つの数なので、それを先に渡せば Host は `end` の瞬間に判定できる。値を凍結してサーバにも保存すれば、Host とサーバの判定は同じ入力・同じ閾値で必ず一致する。応答は表示（偏差値）にしか使わず、進行から外れる。

凍結するのはランの作成時で、手番ごとではない。分布に入るのは等速の結果だけ（`scoring.md` A.4）なので、1 回のラン（長くて十数分）の間に閾値が動いても意味のある差にならない。同じゲームが周回で戻ってきたときに閾値が同じであるほうが、遊ぶ側にも説明しやすい。

不正（ミスを無視して遊び続ける、ミスの結果を送らない）は記録の足し方で防ぐ。記録は手番の順にしか足されず、3 回目のミスで閉じるので、クライアントを改変しても記録は伸びない。ミスの結果を送らなければ、その後ろの手番も記録に入らない（F9）。skip を偽って送ればミスを避けられる（遊ぶ側の申告を信じる。読み込みも満了もサーバからは確かめられない）。ただし skip にしたゲームは以後の周回に出ないので、1 つのゲームにつき 1 回までで、山札が減るぶん到達本数は伸びない。読み込みの skip は 1 つのランで 2 回までで、3 回目でランは記録にならない（A.6）。満了と `error` を偽ると、そのゲームの失敗の数が増える（`scoring.md` A.4。1 ユーザー 5 件の窓の中）。

## B.3 skip が手番を消費する理由

消費しないと、読み込みが遅い端末や固まるゲームが続いたときにランが終わらない（F6）。「50 本」は「50 回の幕間」の意味で、成立した手番の数ではない。成績表の分母からは外すので、記録の意味では損をしない。

読み込みの skip を待たずに決め、以後の周回に出さず、3 本で通信エラーにする理由（#151）: 2026-11-07 の設計は幕間を最大 3 秒延長して待っていた。出せなくなった投稿（`moderation.md` A.3）は待っても読めないので、周回のたびに 3 秒止まる。待たなければ止まらず、位置を飛ばせば次の周回で同じ失敗をしない。3 本読めないのはゲームの側でなく回線の側の問題なので、成績表にせず通信エラーとしてやり直してもらう。位置を飛ばすのは満了と `error` も同じにした（#162。固まるゲームが周回のたびに戻ってこない。skip の規則が 1 つになる）。通信エラーに数えるのは読み込みの skip だけ（満了と `error` はゲームの側の問題で、`scoring.md` A.7 の失敗率で捕まえる）。延長をやめたぶん、遅い回線では読み込みの skip と通信エラーが増える。これは救わない。先読みが 2 手番ぶん先に始まっても間に合わない回線では、サイトを開くことも最初のゲームを読み込むことも難しく、ランとして成り立たない（2026-11-15、オーナー）。却下した案: 3 本続いたら中断して成績表を出す（回線のせいで短くなったランが記録に残る）。サーバが出せなくなった投稿を結果の応答で知らせる（規則が 1 つ増える。読み込めなければ分かる）。

作成時点で出せない投稿を計画に入れない理由（#175）: 以前は `from_run` が投稿状態を見直さずに山札を写し、デイリーは「10 手番のまま、出せない位置は —」だった。出せない投稿は Host から見ると読み込みの skip なので、3 本あると、その共有リンクやその日のデイリーは誰が遊んでも通信エラーで終わる。「3 本読めないのは回線の側の問題」という上の前提が、作成時に分かっている原因で崩れていた。サーバが知っていることを Host に推測させなければ、読み込みの skip の原因はラン中の変化と回線だけになり、前提が成り立つ。ラン中に 3 本が出せなくなる場合（数分の間に 3 本の制限）は区別できないので通信エラーのままにする。却下した案: (a) 計画に「出せない位置」の印を付けて Host が読み込まずに skip にする（遊んでいない手番が到達本数に入り、何も起きていない手番の結果を送ることになる）。(b) デイリーの記号列の位置を揃えるために位置だけ残す（位置を人と見比べることは重要でない。2026-11-18、オーナー）。(c) ランの開始前に山札を全部読み込んでおく（iframe は 3 枚まで。ダウンロードだけ済ませても、配信のキャッシュは制限を効かせるため 60 秒で、残るかはブラウザ次第なので、読めなかったときの規則は無くせない）。(d) デイリーの間はお題の投稿を制限・削除できなくする（いちばん多く遊ばれる投稿を止められなくなる）。

`from_run` で校正状態も見直す理由（#175、Codex のレビュー）: 当初の案は投稿状態だけを見て、`review` / `invalid` になった投稿は「配信はされるので読み込みの skip にならない」として残していた。これだと「配信されるか」と「ランに出せるか」の 2 つの基準ができ、新規のランには出ない固まるゲーム（`invalid`）が共有リンクでは出てくる。基準を `post_eligibility` の 1 つにした（2026-11-18、オーナー）。

最初の手番に時間切れを置く理由（#175）: 「INITED になるまでスタートを受け付けない」だけだと、最初の手番が読めないときにスタートも skip もできず止まる（`verification/Run_firstwait.cfg` で F6 に反例）。幕間の代わりに 10 秒待ち、あとは他の手番と同じ規則にする。

読み込みの skip（A.5 の 6）で空いたスロットを計画の次の手番で埋めるのも同じ理由。埋めないと、先読み 2 枚が続けて skip になったときに次の手番がなく、ランが終わらない（形式検証 `verification/Run_literal.cfg` で F6 が破れる、#72）。スロットを位置と読めば、生きている iframe は 3 枚を超えない（F3）。

## B.4 戻る操作を持たない理由

テンポを守るため。1 本 3〜10 秒のゲームで「さっきのをもう一回」を許すと、ランの長さも速度の意味も崩れる。遊び直したいゲームはゲームページで単発で遊べる。N−1 の iframe を持たないので、同時に生きる iframe が 1 枚減る副産物もある。

## B.5 山札を 12 本にした理由（暫定）

周回の意味を作るため。エンドレスの面白さは「同じゲームが速くなって戻ってくる」駆け引きで、プールが数百本だと 50 手番では一周しない。12 本なら 4〜5 周で、1 周目は初見、2 周目から慣れが効き、5 周目は 1.5 倍で苦しい、という山ができる。本数は初見の多さと慣れの効き方のトレードオフなので実機で変える。

## B.6 幕間で「新作」を知らせない理由

知らせると遊ぶ側が手を抜く。新作枠の目的は校正用の記録を集めることなので、本気で遊んでもらう必要がある。残機が減らないことは結果フラッシュで分かれば十分。

## B.7 速度を 1/8 刻みにした理由

連続値にすると、リプレイの再現と検証のためにセッションごとに任意の実数を保存することになる。5 値なら `speed` の意味を人が読めるし、`protocol.md` の未解決（離散か連続か）もここで閉じる。

## B.8 先読みを `required` アセットまでにする理由

N+1, N+2 の 2 枚ぶんを常に裏でロードしている。全アセット（3 MB）を 2 枚ぶん読むとモバイル回線で手番より通信が長くなる。`required` の上限 512 KB で、先読みは最大 2 × 640 KB 程度に収まる。MVP ではアセット自体がないので実質コードだけ。

## B.9 中断したランを再開できない理由

再開には、Host が記録から残機と次の手番を組み直し、iframe を作り直す必要がある。10 分の中断後に速度 1.375 の 4 周目から再開する体験は、遊ぶ側にも良くない。中断の結果はそのまま成績表になり、同じ山札で遊び直すのは `from_run` で足りる。

## B.10 校正済みが足りないとき、未校正で埋める理由（#123）

サービス開始時は校正済みが 0 本で、未校正のゲームが記録を集める場所は新作枠しかない。規定どおり「校正済み 11 本 + 新作枠 1 本」を要求すると、ランが始まらず、どのゲームも校正されない。埋めた手番はミスにならないので、校正済みが 0 本の間のエンドレスは「ミスの起きない 50 手番」になるが、身内で校正を踏む期間の話なので受け入れる。校正済みが 11 本を超えれば、この規則は使われなくなる。

却下した案: 運営が手で `calibrated` にする（n < 20 で偏差値が出てしまい、`scoring.md` A.5 と食い違う）。ゲームページの単発プレイで踏んでからランを開く（ランを試せるのが 12 本 × 20 プレイの後になる）。同じゲームを山札に重ねる（1 周目から同じゲームが戻ってきて、周回と速度の意味が崩れる）。
