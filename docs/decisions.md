# 決定の記録（ADR）

仕様に関わる決定を、理由と影響範囲つきで時系列に残す。番号で参照する（例: `D-002`）。
取り消した決定は消さず「取消」と書いて、取り消した決定の番号を添える。

形式: 日付 / 状態（有効・取消・一部取消）/ 文脈 / 決定 / 理由 / 影響 / 関連 Issue・PR。

## D-002 ゲームの結果を勝敗から「点数＋順位ベースの偏差値」に変える

2026-11-06 / 有効 / #43

**文脈**: 勝敗 2 値だと記録が「7/10」のような分散の小さい数字になり、やり直せるので誰の 7/10 でも同じに見える。作る側も「どれだけ耐えたか・正確か」を表現できない。WarioWare から離れた独自の顔も欲しい。

**決定**:
- ゲームは整数の点数を 1 回報告する。大きいほど良い。勝敗は廃止。勝敗が自然なゲームは 0 / 1 を報告する
- ゲームごとの偏差値を「遊んだ人の中での順位」から出す: 50 + 10 × Φ⁻¹(パーセンタイル)。平均と標準偏差からは出さない
- 20 プレイで校正済み。それまでは作者が宣言する `gf:target` を仮基準にして `min(1, 点数 / target)` を表示する。校正後は target を使わない
- 過去のラン結果は確定時の値で凍結する

**理由**: 偏差値は上が開いている（上位 0.1% ≈ 81）ので記録として伸び、平均が取れるので総合に使える。大学生に馴染みがある。順位から出すのは、ゲームの点数分布が正規分布から遠く（0 張り付き・長い尾・二峰）、素の偏差値だと外れ値 1 人で破綻するため。作者の点数を基準にする案は、作者が手を抜く・上手すぎる・自分のゲームをやり込んでいるとは限らない、の 3 点で退けたが、仮基準としてなら害がないので残した。

**影響**: `game-contract.md`（点数の規約、`gf:target`）、`protocol.md`（`end` のペイロードから `result` を外す）、`scoring.md`（計算、校正）、`data-model.md`（`sessions.score`、校正状態）。既存の `packages/domain` 静的解析（`win` / `lose` の契約）と `apps/api` スキーマは追従が要る。

**取消したもの**: 旧 `spec.md` 6.3「結果は win か lose を 1 回だけ報告」。

## D-003 エンドレスを主戦場にし、デイリーは成績表の習慣化フックにする

2026-11-06 / 有効 / #43

**文脈**: お題 10 本固定のランは、全員同じ 10 本で勝敗だけだと面白い記録にならない。エンドレスは速くなる・不意打ち・失敗が笑える、という面白さがあり、AI 生成でゲームの数が多いことが初めて武器になる。

**決定**:
- エンドレス: 校正済みの公開ゲーム全体から出題。速度は論理時間の進みを速める方式で上限 1.5 倍。残機 3、偏差値 40 未満でミス。記録は到達本数。上限 50 本
- デイリー: 運営のお題 10 本、順序はお題と日付で固定。記録は平均偏差値と判定（A〜E）。記号列で共有
- 新作枠（10 本に 1 本）は両方にあり、点数は成績に入らず残機も減らない
- 出題順はラン作成時に確定、ゲーム内の乱数シードはセッションごと

**理由**: 「勝敗か点数か」と「エンドレスかデイリーか」は独立の軸なので両方取る。速度を論理時間で上げるのは、ゲームの中身を変えずリプレイも検証もそのまま効くため。ランの長さに上限を置くのは「ランは必ず終わる」を検証可能にするためと、`runs` の配列を有界にするため。

**影響**: `run.md`（モード、速度、残機、上限、プール）、`protocol.md`（`init.speed`）、`game-contract.md`（1.5 倍でも成立すること）、`data-model.md`（`runs.mode`、`theme_id` NULL 可）、`verification/Run.tla`（有限性）。

## D-004 ゲームの一生に「新作枠」と「校正」を置き、モデレーションとは別の軸にする

2026-11-06 / 有効 / #43

**文脈**: 順位ベースの偏差値は記録が貯まるまで出せない。個々のゲームにランへ入るまでの助走が要る。

**決定**:
- 投稿直後 → 新作枠 → 校正済み（20 プレイ）→ 不成立 / 要確認、の校正状態を `posts` に持つ
- 分布の形で「成立しているか」「不正か」を検査する（`product.md` 5.4）。閾値は 20 プレイから
- 校正状態はモデレーションの投稿状態（`pending` / `limited` / `public` / `restricted` / `removed`）とは別の軸。両方で問題がないゲームだけがランに入る
- 校正済みになった時点で作者に通知する
- サービス開始時の 100 本は運営が自作し、公開前に 20 プレイずつ踏む

**理由**: TikTok の初期配信と同じ構造で、小さく配って反応を見て広げる。作る側には「ランに入りました」が最大のフック。校正状態をモデレーションと混ぜないのは、「ゲームとして壊れている」と「内容が不適切」で処置も通知も違うため。

**影響**: `scoring.md`、`data-model.md`（`posts.calibration`、分布の集計）、`run.md`（新作枠の混ぜ方）、`verification/Lifecycle.tla`。

## D-005 Showcase を廃止し、プレビューと共有物はサーバがリプレイから描画する

2026-11-06 / 有効 / #43

**文脈**: 旧仕様では Showcase（作者が録る代表リプレイ）が public の条件かどうかで 3 箇所が矛盾していた。一覧には動く絵が要るが、iframe は一覧では重すぎる。クライアントの `captureStream` は iOS Safari で動く保証がない。

**決定**:
- Showcase を廃止する。公開条件にしない。`expired` 状態も不要
- 静止サムネは投稿時に「入力なしで 90 フレーム目」をサーバが描画する
- プレビュー動画は「誰かの初プレイ」のリプレイから 2 秒をサーバが切り出す（MP4/WebM、音なし、100〜200 KB）。GIF は使わない
- 共有用の成績表画像・クリップもサーバで作る。クライアントの `MediaRecorder` 経路は持たない

**理由**: 決定論性があるので headless Chromium でリプレイを描画できる。スコア検証と同じ基盤で、新しい部品が要らない。iOS の録画可否という未検証事項が消える。

**影響**: `product.md` 8、`scoring.md`（描画ワーカー）、`data-model.md`（`posts.thumb_key` / `preview_key`、`showcase_key` 廃止）、`protocol.md`（`media` メッセージの要否を再検討）、`moderation.md`（`pending → public` の条件から Showcase を外す）。

**取消したもの**: 旧 `spec.md` 7.3 の Showcase、7.4 のクライアント録画、9.2 手順 7、12.2 I4。

## D-006 ゲームの長さを 3〜10 秒にし、時間切れを必ず置く

2026-11-06 / 有効 / #43

**文脈**: 点数制で「ゲームオーバーまで」を許すと上手い人ほど 1 本が長くなり、ランの長さが読めず、長い＝高得点の構造で公平性が崩れる。一方 5 秒固定は点数の幅を殺す。

**決定**: 宣言できる長さは 3〜10 秒（論理 180〜600 フレーム）。時間切れは必ず来る。ゲームオーバーで早く終わるのも、明示的に終わるのも可。10 秒超は受け付けない。1.5 倍速でも成立することを求める。

**影響**: `game-contract.md`、静的解析の範囲（180〜480 → 180〜600）。

**取消したもの**: 旧 `spec.md` 6.3「180〜480 フレーム」。

## D-007 勝敗・点数の保存先は `sessions`、`runs` は集計だけ持つ

2026-11-06 / 有効 / #43

**文脈**: 旧仕様は `sessions` に結果の列がなく `runs.results[]` と二重だった。`games` に `theme_id` / `verb` / `thumb_key` を足していたが、`games` はハッシュで重複排除される不変コンテンツなので同じ HTML を別のお題に出すと壊れる。

**決定**: 点数・検証結果はセッション単位が真実（`sessions.score`、`verdict`）。`runs` はセッションの集計（到達本数、平均偏差値、凍結した成績表）を持つ。お題・動詞・入力・サムネなど投稿に属する属性は `posts` に置き、`games` は内容とハッシュだけ。

**影響**: `data-model.md`。既存の `apps/api` スキーマ（`games.theme_id` 等）は追従が要る。

## D-008 読み込み失敗は `skip` にして負けと区別する

2026-11-06 / 有効 / #43

**決定**: 幕間の延長上限を超えて `start` できなかったゲームは `skip`。成績に入れず、残機も減らさず、成績表の分母からも外す。

**理由**: 回線起因の失敗が記録に混ざると、記録も計測も汚れる。

**影響**: `run.md`、`data-model.md`（`sessions.state` に `skipped`）。

## D-009 出題順はランで決め、ゲーム内の乱数シードはセッションごとに発行する

2026-11-06 / 有効 / #43

**文脈**: 旧仕様に「play のたびにサーバが発行」と「ランのシードはお題と日付」が並び、どちらが乱数を決めるのか曖昧だった。

**決定**: 順序（どのゲームがどの順で出るか）はラン作成時に確定し、共有リンクで再現できる。ゲーム内の乱数シードは 1 セッションごとにサーバが発行し、同じシードで複数回は遊べない。友達と同じ順で遊べれば十分で、同じ乱数まで揃えない。

**影響**: `run.md`、`scoring.md`（リプレイログの使い回し防止）。

## D-010 BGM をゲーム単位のアセットから外す

2026-11-06 / 有効 / #43

**文脈**: 10 秒以内のゲームで、`required` にできない 512 KB の BGM を `start` 後に読む規約では、再生前にゲームが終わる。

**決定**: ゲームのアセット種別から BGM を外す。効果音（Opus、64 KB）は残す。ランやお題の単位で Host が BGM を鳴らす方式を暫定とする。

**影響**: `game-contract.md` 4.2 相当、`data-model.md`（`assets.type` から `bgm`）。
