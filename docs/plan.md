# GameFeed プロジェクト計画（MVP 8週間）

Oct 29, 2026 作成 · Nov 3, 2026 改訂（ミクロゲーム・MCP一本・趣味前提） · @Takuya Sakuma

## 1. 前提と目標

GameFeedは個人の趣味プロジェクトとして進める（会社への持ち込みは行わない）。対象は大学生、中身はワリオ式ミクロゲーム（5秒・動詞ひとつ・入力ひとつ）をお題ごとに連続で遊ぶフィード。投稿は自分のAI（Muse・Claude等）に接続プロンプトを1つ貼るだけでつながるMCP経由を主経路とする。

稼働は週30時間（約4人日）、8週間で32人日。MVP公開目標は Dec 27, 2026（W8末）、バッファは年末年始を含め Jan 11, 2027 まで。趣味なので締切のために品質を落とさず、遅れたら延ばす。ただし公開日を決めないと終わらないので目標は置く。

MVPは「お題のランを連続で遊べて、自分のAIから1プロンプトで投稿できる」体験を検証するためのもので、ユーザー獲得や収益は目標にしない。マーケ資料（競合調査 第9節）のPoC（作り手10人・遊び手10人）をクローズドβとして兼ねる。

**MVP完了条件（すべて満たして公開）**

- [ ] Gate 0: サンドボックス侵入テストのチェックリスト（仕様書15章 #1）を全項目クリア
- [ ] MuseとClaudeのそれぞれで、サイトの接続プロンプトを貼るだけでコネクタ登録が完了し、`publish_game` で投稿したミクロゲームがお題のランに並ぶ
- [ ] お題ランを開く → 5秒ゲームが幕間を挟んで自動で続く → 勝敗表示 → ラン結果画面、が iOS Safari と Android Chrome で動く
- [ ] リプレイ動画（縦・短尺）を書き出してストーリーズやXに貼れる
- [ ] 投稿状態の変更、通報、アカウント単位の一括非公開が運営画面から1分以内にできる
- [ ] 仕様書14章の計測指標がSQLで取れる
- [ ] 自作ミクロゲーム30本（お題3つ分）と、外部協力者3名以上の投稿がランに載っている
- [ ] 利用規約・プライバシーポリシー・削除申請窓口が公開されている

## 5. 先に決める技術判断

Nov 3, 2026 に改訂。前提は趣味の個人開発なので、判断基準は「月額ゼロで始める、デプロイ先は最少、運用作業ゼロ、認証とTLSは自前で持たない」。会社への移管は考えず、移植性のための制約は置かない。

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| アプリ本体・API・MCP | Vite＋React の SPA と Hono の API を Vercel Hobby に1プロジェクトで。フロントは `apps/web`、API・MCPサーバは `apps/api`（Hono、`api/index.ts` から配る）、ゲーム配信は `apps/games`（Cloudflare Worker）、SDKは `packages/sdk`。共有リンクの OGP だけ Hono の `/r/:id` で HTML を返す。PWA は `vite-plugin-pwa`（W6、0.5人日） | React の経験はあるが Next.js は未経験で、SSR も SEO も要らない構造（ゲームは iframe、殻はアプリ）なので、概念の少ない SPA＋API が最短。Hono は Cloudflare Workers にもそのまま載るので、後で全部 Cloudflare に寄せる道も残る。Hobby は非商用限定なので、スポンサー収益を入れる段で有料化 |
| DB | Supabase 無料枠の Postgres | 無料で十分。固有機能を使っても構わない |
| ログインと認可サーバ | Better Auth（Googleログイン）＋MCPプラグイン。アプリ自身が OAuth 2.1 の認可サーバになり、DCR・PKCE・`.well-known` を出す。MCPルートは Hono の `@hono/mcp` ミドルウェア | Museのカスタムコネクタは DCR＋OAuth が必須（認証なしはコネクタとして登録されない）。W1初日にMuseとClaudeの実機PoC。だめなら Cloudflare `workers-oauth-provider` に切替 |
| トークン方針 | アクセストークン24時間以上、リフレッシュトークン30日、ローテーション後も旧トークンに猶予を持たせる | 検証記事では、コールドスタート中の再試行と1時間で切れるリフレッシュトークンで401が頻発した。Vercelはコールドスタートが短いが猶予は入れる |
| MCPツール | `publish_game`（同一内容は上書き）、`list_my_games`、`unpublish_game` の3つと、SDKの約束事を返すリソース1つ | Museのカスタムコネクタはツール単位の許可設定がないので、最小・非破壊に保つ |
| 投稿の入口 | サイトに「このプロンプトをMuse/Claudeに貼る」のコピーボタン1つ。接続後は「GameFeedにこのゲームを投稿して」で完了 | 手軽でないと誰も投稿しない。貼り付けフォームは受け皿として後回し（#16） |
| ゲームHTMLの保存と配信 | Cloudflare R2＋Worker。別ドメインのDNSを Cloudflare に置き、Universal SSL のワイルドカード証明書を自動発行。Worker が R2 から読んで CSP を付けて返す | 別オリジンは自前で代替不可。証明書は自動。無料枠で足りる |
| 対象端末 | iOS Safari は現行と1つ前のメジャー、Android Chrome は最新。デスクトップは「動けばよい」。W4 の実機確認は iPhone 実機1台を必須 | ランはモバイル縦画面が主。Safari の iframe・音声・性能の癖は実機でしか分からない |
| 状態機械の実装 | ライブラリは入れず、仕様書13章の TLA+ をミクロゲーム向け（制限時間・勝敗・幕間）に拡張してから、状態名・遷移名をそのまま TypeScript の union 型＋遷移テーブルに写す。不変条件は Vitest で検証 | 検証済みモデルと実装の乖離を防ぐ |
| 計測の保存先 | Postgres のイベントテーブル1枚。集計は SQL ビュー | MVP 規模では十分 |

**趣味のルール**

- 月額ゼロで始める。有料化するのは「人が遊んでいて無料枠を超えた」ときだけ
- デプロイはボタン1つ（Vercel の Git 連携、Worker は `wrangler deploy`）。手順書が要る運用は作らない
- ベンダーロックインは受け入れる。抽象化層を作らない
- 面白くない作業はAIに任せ、自分はゲームのテンポとSDKの手触りに時間を使う

## 6. リスクと対策

最大のリスクは工数（37人日 vs 32人日）と、Muse／Claudeとの接続が安定するかの2つ。仕様書15章の技術リスクのうち、MVP公開を止めるのはサンドボックス突破だけとする。

| リスク | 兆候 | 対策 | 判断点 |
| --- | --- | --- | --- |
| 工数超過 | W4末時点で #1〜#7 のうち完了が5件未満 | 第4節の「削る順番」を上から適用。それでも足りなければ公開を年明け（Jan 11, 2027 まで）に延ばし、それ以上は延ばさない | W4末 |
| MuseからOAuth/DCRで繋がらない | W1 PoC でMuseのコネクタ画面に登録されない、または `publish_game` ダミーが通らない | Better Auth → Cloudflare `workers-oauth-provider` に切替（＋1人日）。それでもだめなら Claude コネクタ＋貼り付けフォームでMVPを出し、Muse は Phase 2 | W1末 |
| トークン更新で401が頻発 | βで「再認証してください」が1日に複数回出る | アクセストークンを延ばす、旧リフレッシュトークンの猶予を広げる。再認証の手順をサイトに書いておく | W5、W7 |
| サンドボックス突破 | 侵入テストで `blob:` ナビゲーション、Service Worker 登録、親フレーム参照のどれかが通る | 公開しない。CSP・sandbox 属性の見直し後に再テスト。これだけはスケジュールより優先 | W2末（Gate 0） |
| iOS Safari の挙動差 | iframe 内音声が鳴らない、幕間の切替がもたつく、メモリで落ちる | W4 の最初に実機で先読み構成を試す。だめなら先読みを1本に減らす | W4前半 |
| 5秒ゲームが「同じようなもの」に感じる | サンプル30本の連続プレイで自分が3分持たない | お題でテーマを縛る、動詞の型（押す・避ける・合わせる…）を分散させる、幕間の演出で緩急をつける。W3で自分、W7で大学生に試す | W3、W7 |
| AIがミクロゲームの型を守らない | 自作30本のうち準拠チェックで5本以上拒否される | SDKガイドリソースと接続プロンプトを書き直し、`publish_game` のエラー文に修正方法を含める | W3、W7 |
| 決定論性のずれ | 同じログの再生が端末で違う結果になる | MVPではリプレイは「参考映像」扱い。検証は Phase 2 | 公開を止めない |
| 一人開発の中断・飽き | 1週間まるごと進捗ゼロ | 週次レビューで再計画。「最小公開セット」= #1,2,3,6,9,10,15 は守り、残りは落とす。趣味なので延びてもよいが、やめるなら明示的にやめる | 毎週 |
| 不適切投稿・スパム | βで通報が出る、同一アカウントから大量投稿 | 新規5件/日の上限と全件サムネ目視は MVP から。一括非公開を W6 までに動かす | W6 |
| 法務の抜け | 規約・削除窓口がない状態で外部ユーザーが投稿 | W7 に雛形から作成。協力者への案内は規約公開後 | W7 |

## 7. 進め方のルール

毎週金曜に30分の週次レビューをこのチャットで行い、この計画書の第8節とWBSの進捗を更新する。レビューの形式は「完了したこと・終わらなかったこと・来週やること・削る判断の要否」の4点だけ。

- **タスク粒度**：半日〜1日で終わる単位に切る。2日を超える作業は分割する
- **実装**：Claude Code で進め、コミットメッセージとPRに仕様書の章番号（例 `spec#6.3`）を付ける。仕様書と実装がずれたら仕様書を直す
- **完了の定義**：本番環境で動く＋テストがある＋仕様書の該当章と矛盾がない。ローカルで動くだけは「進行中」
- **スコープ変更**：思いついた機能は「Phase 2 以降」リストに追記するだけにする。MVPに入れるのは、同じ人日を第4節から削ったときだけ
- **品質ゲート**：Gate 0 のチェックリストは書面にし、結果を計画書に残す。Host状態機械の不変条件（RUNNING が同時に2つない、`end` は1回だけ）は自動テストにする
- **計測**：4指標は公開初日から取る。計測コードは後回しにしない
- **AI活用**：サンプルゲーム生成、テストコード、利用規約の雛形、侵入テスト項目の洗い出しはAIに任せ、設計判断とレビューは自分で行う
