# GameFeed プロジェクト計画（MVP 8週間）

Oct 29, 2026 作成 · Nov 3, 2026 改訂（ミクロゲーム・MCP一本・趣味前提） · Nov 14, 2026 改訂（`product.md` に追従: 点数と偏差値、エンドレス、成績表、下書き → 公開 → 校正。#122） · @Takuya Sakuma

## 1. 前提と目標

GameFeedは個人の趣味プロジェクトとして進める（会社への持ち込みは行わない）。対象は大学生、中身は AI で作られた 3〜10 秒のミニゲーム（動詞ひとつ・入力ひとつ）を幕間を挟んで連続で遊び、ゲームごとの偏差値と成績表をもらうラン（`product.md` 1）。主戦場はエンドレス、習慣化のフックがデイリー（`product.md` 4）。投稿は自分のAI（Muse・Claude等）に接続プロンプトを1つ貼るだけでつながるMCP経由を主経路とする。

稼働は週30時間（約4人日）、8週間で32人日。MVP公開目標は Dec 27, 2026（W8末）、バッファは年末年始を含め Jan 11, 2027 まで。趣味なので締切のために品質を落とさず、遅れたら延ばす。ただし公開日を決めないと終わらないので目標は置く。

MVPは「ランを連続で遊べて、自分のAIから1プロンプトで投稿できる」体験を検証するためのもので、ユーザー獲得や収益は目標にしない。マーケ資料（競合調査 第9節）のPoC（作り手10人・遊び手10人）をクローズドβとして兼ねる。

**MVP完了条件（すべて満たして公開）**

- [ ] Gate 0: サンドボックス侵入テスト（`docs/manual-tests/sandbox-pentest.md`、`security-checklist.md`）を全項目クリア
- [ ] MuseとClaudeのそれぞれで、サイトの接続プロンプトを貼るだけでコネクタ登録が完了し、`publish_game` で下書き → 試遊ページで遊ぶ → 公開、まで通る（`product.md` 9）
- [ ] 公開したゲームが新作枠に入り、20 プレイで校正済みになって正規枠に入る（`product.md` 7、sc#A.7）
- [ ] エンドレス: スタート → 幕間 → 3〜10 秒のゲーム → 結果フラッシュ → … → 成績表（到達本数とゲームごとの偏差値）が iOS Safari と Android Chrome で動く（run#A.5、A.7、A.11）
- [ ] デイリー: お題 1 つ 10 本を遊び、平均偏差値と記号列が出る（run#A.2）
- [ ] 成績表を画像として共有でき、共有リンク（`/r/<run_id>`）から同じ山札で遊べる（`product.md` 8、run#A.14）
- [ ] 投稿状態の変更、通報、アカウント・ツリー単位の一括制限が運営画面から1分以内にできる（`moderation.md`）
- [ ] 計測指標（ラン完走率・平均プレイ時間・共有数・投稿完了率）がSQLで取れる
- [ ] 校正済みの自作ゲーム 30 本（うちお題 1 つ分の 10 本）と、外部協力者3名以上の投稿がランに載っている（**本数は未決**。`product.md` 7 は「最初の 100 本」。下の第 5 節）
- [ ] 利用規約・プライバシーポリシー・削除申請窓口が公開されている

## 5. 先に決める技術判断

Nov 3, 2026 に改訂、Nov 14, 2026 に実装済みの判断を反映。前提は趣味の個人開発なので、判断基準は「月額ゼロで始める、デプロイ先は最少、運用作業ゼロ、認証とTLSは自前で持たない」。会社への移管は考えず、移植性のための制約は置かない。

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| アプリ本体・API・MCP | Vite＋React の SPA と Hono の API を Vercel Hobby に1プロジェクトで。フロントは `apps/web`、API・MCPサーバは `apps/api`（Hono、`api/index.ts` から配る）、ゲーム配信は `apps/games`（Cloudflare Worker）、SDKは `packages/sdk`。共有リンクの OGP だけ Hono の `/r/:id` で HTML を返す。PWA は Phase 2 | React の経験はあるが Next.js は未経験で、SSR も SEO も要らない構造（ゲームは iframe、殻はアプリ）なので、概念の少ない SPA＋API が最短。Hono は Cloudflare Workers にもそのまま載るので、後で全部 Cloudflare に寄せる道も残る。Hobby は非商用限定なので、スポンサー収益を入れる段で有料化 |
| DB | Supabase 無料枠の Postgres | 無料で十分。固有機能を使っても構わない |
| ログインと認可サーバ | Better Auth（Googleログイン）＋MCPプラグイン。アプリ自身が OAuth 2.1 の認可サーバになり、DCR・CIMD・PKCE・`.well-known` を出す（`@better-auth/mcp`）。MCPルートは MCP 公式 SDK v2 の `createMcpHandler` | Museのカスタムコネクタは DCR＋OAuth が必須（認証なしはコネクタとして登録されない）。2026-11-05 に Muse と Claude の実機で通った（#5）。切替は不要になった |
| トークン方針 | アクセストークン24時間以上、リフレッシュトークン30日、ローテーション後も旧トークンに猶予を持たせる | 検証記事では、コールドスタート中の再試行と1時間で切れるリフレッシュトークンで401が頻発した。Vercelはコールドスタートが短いが猶予は入れる |
| MCPツール | `publish_game`（下書き → `publish: true` で公開。同一内容は `reused`）、`list_my_games`、`unpublish_game` の3つと、SDKの約束事を返すリソース1つ | Museのカスタムコネクタはツール単位の許可設定がないので、最小・非破壊に保つ |
| 投稿の入口 | サイトに「このプロンプトをMuse/Claudeに貼る」のコピーボタン1つ。接続後は「GameFeedにこのゲームを投稿して」で完了 | 手軽でないと誰も投稿しない。貼り付けフォームは受け皿として後回し（#16） |
| ゲームHTMLの保存と配信 | Cloudflare R2＋KV＋Worker。配信オリジンは `workers.dev` の 1 つで、投稿は `/p/<post_id>/` のパスで分け、投稿ごとの CSP と `sandbox` で隔離する（#21、se#A.1）。Worker が KV の配信可否を見て R2 から読み、SDK を注入して返す | 別オリジンは自前で代替不可。ドメインを買わずに済む。無料枠で足りる |
| 対象端末 | iOS Safari は現行と1つ前のメジャー、Android Chrome は最新。デスクトップは「動けばよい」。W4 の実機確認は iPhone 実機1台を必須 | ランはモバイル縦画面が主。Safari の iframe・音声・性能の癖は実機でしか分からない |
| 状態機械の実装 | ライブラリは入れず、`verification/` の TLA+（`Session` / `Run` / `Lifecycle` / `Moderation`、#68）の状態名・遷移名をそのまま TypeScript の union 型＋遷移テーブルに写す。不変条件は Vitest で検証。セッションは済み（#52）、ランは #130 | 検証済みモデルと実装の乖離を防ぐ |
| 計測の保存先 | Postgres のイベントテーブル1枚。集計は SQL ビュー | MVP 規模では十分 |
| サーバの描画・実行ハーネス（**未決**） | sc#A.10 は headless Chromium で Host を動かす（公開前の実行チェック、サムネ、成績表の画像）。候補: (a) GitHub Actions のジョブ（無料、起動に 30 秒〜、公開ボタンの同期チェックには遅い）(b) Cloudflare Browser Rendering（Worker から使える。無料枠は 1 日 10 分）(c) Vercel の関数に軽量 Chromium（Hobby の実行時間とサイズの上限に近い） | 月額ゼロの範囲で決める。W5 の着手前にスパイクを 1 本切る。公開前チェックを「公開後すぐの非同期ジョブ」に緩めるなら mc#A.9 / sc#A.10 の変更になる |
| 開始時の自作ゲームの本数（**未決**） | この計画は 30 本（うちデイリー 1 お題分 10 本）。`product.md` 7 は「最初の 100 本」 | 30 本 × 20 プレイ = 600 プレイを身内で踏む必要がある。100 本なら 2,000 プレイ。エンドレスの山札は 12 本なので 30 本で 2〜3 通りの山札が組める |

**趣味のルール**

- 月額ゼロで始める。有料化するのは「人が遊んでいて無料枠を超えた」ときだけ
- デプロイはボタン1つ（Vercel の Git 連携、Worker は `wrangler deploy`）。手順書が要る運用は作らない
- ベンダーロックインは受け入れる。抽象化層を作らない
- 面白くない作業はAIに任せ、自分はゲームのテンポとSDKの手触りに時間を使う

## 6. リスクと対策

最大のリスクは工数（残り 34.5 人日 vs 24 人日）と、ランのテンポが実機で成立するかの2つ。Muse／Claudeとの接続は W1 に通った。技術リスクのうち、MVP公開を止めるのはサンドボックス突破だけとする。

| リスク | 兆候 | 対策 | 判断点 |
| --- | --- | --- | --- |
| 工数超過 | W4末時点で #1〜#7 のうち完了が5件未満 | 第4節の「削る順番」を上から適用。それでも足りなければ公開を年明け（Jan 11, 2027 まで）に延ばし、それ以上は延ばさない | W4末 |

## 7. 進め方のルール

毎週金曜に30分の週次レビューをこのチャットで行い、この計画書の第8節とWBSの進捗を更新する。レビューの形式は「完了したこと・終わらなかったこと・来週やること・削る判断の要否」の4点だけ。

- **タスク粒度**：半日〜1日で終わる単位に切る。2日を超える作業は分割する
- **実装**：Claude Code で進め、コミットメッセージとPRに文書名と節（例 `protocol#A.3`、`run#A.5`）を付ける。文書と実装がずれたら、実装を直すか `type:spec` の Issue で文書を直す（`CLAUDE.md`、`docs/workflow.md`）
- **完了の定義**：本番環境で動く＋テストがある＋文書の該当節と矛盾がない。ローカルで動くだけは「進行中」
- **スコープ変更**：思いついた機能は「Phase 2 以降」リストに追記するだけにする。MVPに入れるのは、同じ人日を第4節から削ったときだけ
- **品質ゲート**：Gate 0 のチェックリストは書面にし、結果を計画書に残す。Host状態機械とランの不変条件（RUNNING が同時に2つない、`end` は1回だけ、run#A.15 の F1〜F9）は形式検証と自動テストにする
- **計測**：4指標は公開初日から取る。計測コードは後回しにしない
- **AI活用**：サンプルゲーム生成、テストコード、利用規約の雛形、侵入テスト項目の洗い出しはAIに任せ、設計判断とレビューは自分で行う
