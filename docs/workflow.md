# 作業の流れ

## Issue
- 単位: 1 Issue = 1 PR で閉じられる大きさ（目安 0.5〜2 人日）。計画書の WBS 1 行は複数 Issue に割る。
- テンプレート `task` を使い、次を必ず埋める:
  - 目的（なぜやるか。1〜2 行）
  - 仕様の参照（文書名と節。例: `protocol#3`、`product#5.2`）と計画書の参照（`plan#n`）
  - 関係する要件 ID（`docs/requirements.md`。なければ先に追加する）
  - テスト層（unit / integration / contract / e2e / manual）と、各層で何を確かめるか
  - 完了条件（チェックリスト。テストが通ること＋目視項目）
- ラベル:
  - `type:*` task / bug / spike / spec（仕様変更の提案）
  - `area:*` web / api / games / sdk / domain / infra / docs
  - `test:*` unit / integration / contract / e2e / manual（主となる検証手段）
  - `blocked` 依存待ち。本文に何を待っているか書く
- マイルストーン: `W1`〜`W8`（計画書 第3節の週）。週次レビューでマイルストーンの残りを見る。
- Spike（調査）は結果を Issue のコメントに書いて閉じる。コードはマージしない。

## ブランチと PR
- `main` は常にデプロイ可能。`main` から `type/<issue>-<slug>` を切る。
- PR は小さく。300 行を超えたら分割を検討する。
- PR 本文（テンプレート）:
  1. 何をしたか（Issue へのリンク、`Closes #N`）
  2. 仕様との対応（どの章のどの文をどう実装したか）
  3. テストで保証したこと（要件 ID と、どの層のテストか）
  4. 保証していないこと（意図的に外したもの、目視で確認したもの）
  5. 確認手順（manual の場合）
- CI（lint / typecheck / test）が緑で、本文が埋まっていて、Codex の P0 / P1 に未対応が残っていなければ squash merge（次節）。コミットメッセージは PR タイトル。
- マージ後にブランチを削除する。

## Codex レビュー
往復を減らすため、レビューは PR ごとに最初の自動レビュー 1 回で終える（#98）。直した箇所に新しい指摘が付き、それを直すとまた付く流れで、#81 は 7 往復、#95 は 8 往復かかった。

- `@codex review` は原則頼まない。頼むのは P0 / P1 を直したときだけで、1 回まで。その再レビューで出た指摘は P0 / P1 だけ対応する。
- 指摘は優先度で扱いを決める。

  | 優先度 | 扱い |
  |---|---|
  | P0 / P1 | その PR で必ず直す |
  | P2 | PR の範囲内で数十行以内に収まり、仕様の変更を伴わなければその PR で直す。それ以外は Issue に切り、リンクを返信する |
  | P3 | 直さない。PR ごとに 1 つの Issue（`Codex P3: #<PR番号>`）にまとめて記録する |

- 仕様の変更が要る指摘は、優先度に関係なく Issue に切ってオーナー判断にする（`type:spec`）。
- 直さない指摘には、理由を 1 行で返信する。直した指摘には、コミットと変更点を返信する。
- マージ条件は CI 緑かつ P0 / P1 の未対応なし。Codex の `has_unresolved_findings` は条件にしない。
- PR 本文の「保証していないこと」に、Issue に回した指摘と直さなかった指摘を書く。

## 週次レビュー（金曜）
- マイルストーンの完了 / 未完了を数え、計画書 第4節の「削る順番」と照らす。
- 未解決事項（`product.md` 10 と各文書末尾）に動きがあれば Issue にする。
- 計画書の「今週のタスク」をオーナーに提案し、承認後に更新する。

## 仕様変更
- 実装中に仕様の穴や矛盾を見つけたら、勝手に解釈せず `type:spec` の Issue を切る。
- Issue には「現状の記述」「問題」「提案」「影響範囲（章・要件 ID）」を書く。
- 該当する `docs/*.md`（`product.md` / `game-contract.md` / `protocol.md` など。対応表は Issue #43）を直す PR（コミットは `spec:`、本文に Issue の「提案」を貼る）を出す。`product.md` の「決定」を変えるなら、却下した案とその理由を規則の隣に残す。この PR だけはオーナーがマージする。マージ後に `docs/requirements.md` を追従させてから実装に戻る。
