# 作業の流れ

## Issue
- 単位: 1 Issue = 1 PR で閉じられる大きさ（目安 0.5〜2 人日）。計画書の WBS 1 行は複数 Issue に割る。
- テンプレート `task` を使い、次を必ず埋める:
  - 目的（なぜやるか。1〜2 行）
  - 仕様書の参照（`spec#x.y`）と計画書の参照（`plan#n`）
  - 関係する要件 ID（`docs/requirements.md`。なければ先に追加する）
  - テスト層（unit / integration / contract / e2e / manual）と、各層で何を確かめるか
  - 完了条件（チェックリスト。テストが通ること＋目視項目）
- ラベル:
  - `type:*` task / bug / spike / spec（仕様変更の提案）
  - `area:*` web / api / games / sdk / domain / infra / docs
  - `test:*` unit / integration / contract / e2e / manual（主となる検証手段）
  - `blocked` 依存待ち。本文に何を待っているか書く
- マイルストーン: `W1`〜`W8`（計画書 第3節の週）。週次レビューでマイルストーンの残りを見る。
- Spike（調査）は結果を Issue のコメントに書いて閉じる。コードはマージしない。

## ブランチと PR
- `main` は常にデプロイ可能。`main` から `type/<issue>-<slug>` を切る。
- PR は小さく。300 行を超えたら分割を検討する。
- PR 本文（テンプレート）:
  1. 何をしたか（Issue へのリンク、`Closes #N`）
  2. 仕様との対応（どの章のどの文をどう実装したか）
  3. テストで保証したこと（要件 ID と、どの層のテストか）
  4. 保証していないこと（意図的に外したもの、目視で確認したもの）
  5. 確認手順（manual の場合）
- CI（lint / typecheck / test）が緑で、本文が埋まっていれば squash merge。コミットメッセージは PR タイトル。
- マージ後にブランチを削除する。

## 週次レビュー（金曜）
- マイルストーンの完了 / 未完了を数え、計画書 第4節の「削る順番」と照らす。
- 未解決事項（spec#15）に動きがあれば Issue にする。
- 計画書の「今週のタスク」をオーナーに提案し、承認後に更新する。

## 仕様変更
- 実装中に仕様の穴や矛盾を見つけたら、勝手に解釈せず `type:spec` の Issue を切る。
- Issue には「現状の記述」「問題」「提案」「影響範囲（章・要件 ID）」を書く。
- `docs/spec.md` を直す PR（コミットは `spec:`、本文に Issue の「提案」を貼る）を出す。この PR だけはオーナーがマージする。マージ後に `docs/requirements.md` を追従させてから実装に戻る。
